Simulated Inference Lab

A three-node k3s cluster on a Windows desktop, running the llm-d inference stack end to end — Gateway API with the Inference Extension, an endpoint picker that routes on KV-cache state, prefill/decode disaggregation, and Prometheus watching all of it. The model servers are simulators; the orchestration is real, and that is the half worth learning.

Host Ryzen 7 9800X3D · 32 GB · Windows 11 Pro · Hyper-V Guests Rocky Linux 9 · 3 × 4 vCPU / 6 GB

What the lab found

Measured on the cluster, including the measurements that went against expectation. Anyone can reproduce a vendor's claim; the useful part is where it stops holding.

82.6%vs 78.4%

Prefix-aware routing beat round-robin on identical traffic — and against the 86.4% ceiling set by 64-token block granularity, that is capturing 96% of the achievable versus 91%. Round-robin recomputes about a quarter more prompt tokens. It cost 2.5× the client latency to do it, because a simulated prefill is nearly free and there is nothing to win back.

74.1%both arms, run 1

The first version of that experiment found nothing, and the reason is the more useful half. 74% turned out to be exactly 192/259 — the shared system prompt and nothing else. Per-user context was 40 tokens, under the 64-token block size, so it could never be cached; the cache held 65,536 tokens so nothing evicted; and with one pod per role the picker logged num-of-candidates: 1. Cache-aware routing needs distinguishing prefixes that span whole blocks, memory scarce enough to evict, and more than one candidate.

95 µsof a 23.8 ms ttft

Scheduling is 0.4% of the request. The endpoint picker sits in the request path — every request waits on it — so this ratio, not the absolute number, is what justifies putting a scheduler there at all. Past roughly 5%, the per-plugin panel says which scorer to drop.

0hrtimer warnings

Two days were lost to a hypervisor, not to Kubernetes. VirtualBox never gets AMD-V on this host — Windows holds the hypervisor for Memory Integrity — so guests ran on NEM and were descheduled for seconds. A 50 ms sleep, 25 samples: multi-second stalls against a flat 51 51 51 … 50 51 on Hyper-V; 14/6/6 hrtimer warnings against zero; load average 13–19 at 73% idle CPU against 0.03.

— 86.4% CEILING · ONLY 5 WHOLE 64-TOKEN BLOCKS OF A 370-TOKEN PROMPT CAN EVER CACHE

The ceiling is the honest denominator. A 370-token prompt holds five complete blocks; the trailing 50 tokens are recomputed by everyone, every time. Against that, prefix-aware routing recovers about a quarter of the recomputation round-robin leaves on the table — 17.4% of tokens against 21.6%.

What this lab can and cannot prove

It can show where the scheduler sends requests, how often caches hit, and what scheduling costs. It cannot say what a cache hit is worth in wall-clock seconds: the model servers are simulators, so the latency figures are properties of their configuration. On a GPU, recomputing 64 prompt tokens costs far more than 8 ms of routing — which is the regime that makes this trade pay, and the one this hardware cannot create.

Four failures that looked like success

Every one of these reported healthy. The pattern is worth more than the individual fixes: find a number that only moves if the work actually happened, and look at it.

A guest with one CPU, reporting four

LOOKED LIKE: a boot hang · WAS: ioapic=off

VirtualBox needs the I/O APIC to run an SMP guest and, without it, silently hands over a single CPU while the configuration still says four. On one vCPU under a nested hypervisor, boots outran Vagrant's timeout — indistinguishable from a hang. The provisioning banner printed CPUS: 1 next to a Vagrantfile saying 4, and it was read past three times. Enabling it took boot from over 600 s to 72.8 s.

Disaggregation enabled, and never happening

LOOKED LIKE: working P/D · WAS: a missing sidecar

Every plugin loaded, the picker logged both scheduling profiles, and no request was ever split. The picker names the prefill pod in a header and expects a proxy in front of the decode server to act on it; there was no such proxy. The only contradicting evidence was a Prometheus counter that did not exist on the prefill pod — a counter that has never incremented is not exported at all, so "absent" meant zero requests, not zero hits.

Metrics endpoint answering 200 with nothing

LOOKED LIKE: a component exporting no metrics · WAS: auth

The picker guards /metrics behind token authentication, and an unauthenticated scrape gets an empty 200 rather than a 401. The token we then supplied was rejected too — because the picker could not check it: it validates tokens through TokenReview, and the chart enables metrics auth without granting itself that right. Binding system:auth-delegator fixed the checker, not the credential.

A benchmark measuring its own setup

LOOKED LIKE: identical results · WAS: three absent preconditions

Both arms returned the same hit ratio to sixteen decimal places, because the query spanned both runs and no scrape had happened yet — a 240-request run finishes in about a second against a 15-second scrape interval. Reading the counters straight off the model servers fixed the measurement; scaling replicas, shrinking the cache and lengthening the prompts fixed the experiment.

Decisions and why

The reasoning is the portfolio material. Anyone can paste install commands.

Hypervisor
Hyper-V, after starting on VirtualBox for familiarity and measuring the cost. Windows keeps a hypervisor resident for Memory Integrity, so VirtualBox never gets AMD-V and falls back to NEM. Memory Integrity stays on: Hyper-V is the hypervisor it requires, so running VMs there removes the indirection rather than fighting it.
Model servers
llm-d-inference-sim, which emits vLLM's own metric names — so the gateway, scheduler, cache accounting and every dashboard panel behave exactly as they would against real vLLM. One assumption was retired along the way: the lab was designed around "the guests have no AVX-512", measured under VirtualBox. Under Hyper-V the full set comes through, so that constraint belonged to the hypervisor. Only 6 GB nodes keep real vLLM out now.
Gateway provider
agentgateway v1.5.0, not Istio or kgateway — kgateway is deprecated, Istio is heavy for 6 GB nodes. Not v1.1.0 either: it watches a v1alpha2.TCPRoute that Gateway API 1.6.2 no longer serves, so its informer blocks forever and the GatewayClass never registers. A controller stuck at 0/1 with no useful log.
Metrics authentication
Left on, and a token issued. Turning --metrics-endpoint-auth off would have made the scrape work in one line. Disabling authentication to make monitoring convenient is not a habit a lab should teach, so Prometheus got a ServiceAccount, a ClusterRole granting GET on the non-resource URL /metrics, and a bearer token.
Dashboards
JSON in git, no Grafana persistence. Dashboards provision from ConfigMaps, so a Grafana restart costs nothing and the UI is never the only copy. The panels are documented by the decision each one drives, not by the metric each one plots.
Secrets
Generated, never committed. The k3s join token is produced at build time into a gitignored file; Grafana's admin password comes from a Secret created out of band. A public repository that rebuilds a whole cluster from one command must not also hand over the keys to it.
Scope
Rook/Ceph, OVN-Kubernetes and Ansible all out. Three OSDs on one SSD is not redundancy; there is no documented k3s + OVN-K path and OpenShift installs it via an operator anyway; and the Vagrantfile already provisions, so a second configuration tool would be ceremony.

Written alongside the work, so the reasoning survives into the write-up rather than being reconstructed afterwards. Every figure on this page came off the running cluster.
