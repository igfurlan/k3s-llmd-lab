Simulated Inference Lab

A three-node k3s cluster on VirtualBox, running the llm-d distributed inference stack. The GPU in this machine is unreachable from the VMs, so the inference is simulated and the orchestration is real — which is the half worth learning.

Host Ryzen 7 9800X3D · 30.8 GB · Windows 11 Pro Guests Rocky Linux 9 · 3 × 4 vCPU / 6 GB

The constraint that shapes everything

Discovered before building, not after. It rewrites phases 4 through 6 and it belongs in the write-up, not hidden.

Real vLLM cannot run in these VMs

  1. 1VirtualBox has no GPU passthrough. The RTX 5070 Ti is invisible to every guest. Not a tuning problem — the feature does not exist.
  2. 2vLLM's CPU backend requires AVX-512. The 9800X3D has it (verified PF_AVX512F: True), but VirtualBox has never exposed AVX-512 to guests.
  3. 3Hyper-V compatibility mode compounds it. Windows keeps a hypervisor resident, so VirtualBox loses nested paging and can drop even plain AVX2 from the guest.

Three independent facts, any one of which is disqualifying on its own.

Now measured, not predicted. The running guests report avx avx2 and nothing beyond — AVX-512 is absent exactly as expected, and point 3's worst case didn't land: AVX2 survived, so ollama gets its fast path.

Resolution

Use llm-d-inference-sim — the llm-d project's own GPU-free vLLM mock. It is OpenAI-API compliant, models prefill and decode latency, degrades under concurrency, and emits vLLM-compatible Prometheus metrics. The gateway, the scheduler, the routing and the entire observability phase exercise identically. Only the tensor math is fake. Real inference comes from ollama, which is built for CPU.

Nine phases

Ordered by dependency, not preference — each phase needs the one above it to be working.

01

Toolchain

Vagrant and VirtualBox installed and verified compatible, project under git.

Verified Vagrant 2.4.9 · VirtualBox 7.2.18 · Git 2.55.0. 2.4.9 is the first Vagrant release supporting VirtualBox 7.2.x.
02

Three Rocky Linux nodes

One Vagrantfile builds all three: static host-only IPs, swap off, firewalld off, SELinux left enforcing, clocks synced with chrony. All three came up clean and reachable on the first successful run.

Built Rocky Linux 9.8 (Blue Onyx) on all three nodes · swap 0B · SELinux Enforcing · firewalld inactive.
Gotcha already hit The registry lists box 6.0.0 as active but its artifact returns 404. Pinned to 5.0.0, which range-GETs clean. Verify artifacts exist — don't trust the metadata.
Cost four hours Every boot after the first appeared to hang. The cause was one setting: ioapic=off. VirtualBox requires the I/O APIC to run an SMP guest and, without it, silently hands over a single CPU while reporting four — no warning, no log line. On one vCPU under a nested hypervisor, boots outran Vagrant's timeout, which is indistinguishable from a hang. Enabling it took boot from exceeding 600s to 72.8s. Written up in postmortem-vagrant.md.
Also configured --paravirtprovider kvm for kvm-clock (a generic Linux guest otherwise reads raw TSC, which drifts badly under a nested hypervisor) · boot_timeout 1800, because boots here are legitimately slow · a 30 GB second disk mounted at /var/lib/rancher, since the box's 8.9 GB root cannot hold the container images this stack needs.
03

k3s cluster

One server, two agents, default Flannel CNI, installed by the Vagrantfile itself — so vagrant destroy -f && vagrant up rebuilds the entire cluster from nothing. OVN-Kubernetes was considered and rejected; see decisions below.

Server flags --node-ip=192.168.56.11 · --flannel-iface=eth1 · --tls-san=192.168.56.11 · --disable=traefik · --write-kubeconfig-mode=0644. Version pinned to v1.36.4+k3s1.
Why the first two flags are mandatory k3s picks its node IP from the default route, which points at the NAT adapter — 10.0.2.15 on all three machines. Without them every node registers under the same address, the cluster forms anyway, and pod networking then fails in ways that look like anything except a networking problem.
Join token Generated once with SecureRandom.hex(32), written to .k3s-token at mode 0600, and read back on every later run. The file is gitignored: a join token is a credential, and this repository is public. Hardcoding one in the Vagrantfile would have been simpler and wrong.
04

Gateway API Inference Extension

Originally "install vLLM on all nodes." That was two mistakes: vLLM can't run here, and llm-d deploys vLLM as pods rather than as a node-level install. The real prerequisite is Gateway API plus the Inference Extension CRDs — the vocabulary that lets a gateway reason about LLM traffic instead of treating it as generic HTTP.

Versions Gateway API v1.4.0+ · Gateway API Inference Extension v1.6.2 (v1-manifests.yaml from the release) · Kubernetes 1.28+ required, cluster runs 1.36.
Gateway provider: agentgateway Three options exist. kgateway is deprecated and being removed. istio is the documented default but heavy for 6 GB nodes. agentgateway is where the project is heading, so the lab starts there rather than learning a path that is on its way out.
05

llm-d on the cluster

Helm-installed from the llm-d-infra chart, with model-server pods backed by the simulator instead of real vLLM. The gateway, the endpoint picker and the routing layer are all genuine — only the tensor math is substituted.

Components Chart llm-d-infra from llm-d-incubation.github.io/llm-d-infra · model servers ghcr.io/llm-d/llm-d-inference-sim:v0.9.0.
One prerequisite we escape The official quickstart needs a HuggingFace token to pull model weights. The simulator downloads nothing, so no token and no secret to manage.
Dead ends worth recording llm-d-modelservice is deprecated — retained only for helmfile guides before v0.7. The chart that matters is oci://ghcr.io/llm-d/charts/llm-d-router-gateway at v0.10.0, with provider.name=none because agentgateway handles the InferencePool natively. Four wrong registry paths preceded it.
The check that prevents version pain llm-d v0.9.0 pins Gateway API Inference Extension v1.5.0 while this cluster runs v1.6.2. Rather than guess, helm template … | grep apiVersion showed the chart emits inference.networking.k8s.io/v1 — exactly what the cluster serves. The v1 API is stable, so the pin was harmless. The same check beforehand would have caught the agentgateway mismatch that cost an hour.
06

Tune llm-d

KV-cache-aware routing, prefill/decode disaggregation, replica scaling. The simulator's configurable latency model makes routing decisions observable in a way a real GPU under load would not.

Prefill and decode, split across the two agents The two phases of inference have opposite performance profiles. Prefill processes the whole prompt in one parallel pass and is compute-bound; decode emits tokens one at a time and is memory-bandwidth-bound. Sharing a pod means sizing for neither. Splitting them lets each scale and be placed independently — on real hardware, prefill on high-compute accelerators and decode on high-bandwidth ones.
How the lab does it k3s-agent-1 is labelled llm-d.ai/role=prefill and k3s-agent-2 llm-d.ai/role=decode; nodeSelector pins each deployment. kubectl get pods -o wide then makes the architecture visible. In production the KV cache must physically move between the two, which llm-d does over NIXL — here that transfer is modelled, not real. The configuration surface and the routing are genuine; the speedup is not, and the write-up says so.
Settled by reading the cluster, not the docs llm-d's GitHub guide describes two InferencePools for P/D; the llm-d.ai docs describe one pool with two labelled Deployments. The running EPP config decides it: one pool, two Deployments, and P/D is an EPP configuration concern. The shipped config carries a single default scheduling profile and no disagg-profile-handler, so the role labels are currently inert. Adding them is what router.epp.pluginsConfigFile exists for. Full detail in epp-scheduling.md.
07

ollama, real inference

A small model — 1B class, quantised — actually generating tokens on CPU. Slow by design, and the honest counterweight to the simulated path.

Depends on The AVX flags reported by phase 2. AVX2 present means usable; AVX-only means slow; neither means painful.
08

A real workload

Drive both endpoints with something that isn't a curl one-liner — concurrent traffic with realistic prompt-length distribution, so the routing layer has decisions to make.

09

Observability and findings

Prometheus and Grafana against the vLLM-compatible metrics the simulator emits: time-to-first-token, inter-token latency, queue depth, cache hit rate. This phase is where the portfolio write-up gets its evidence.

Decisions and why

The reasoning is the portfolio material. Anyone can paste install commands.

Hypervisor
VirtualBox over Hyper-V. Hyper-V would avoid compatibility mode, but familiarity beat a performance margin that doesn't matter for a study lab. Windows keeps a hypervisor resident regardless — every attempt to disable it failed, with Memory Integrity the untested suspect.
Guest OS
Rocky Linux 9 — binary-compatible with RHEL, so the dnf/SELinux/firewalld habits transfer. Rocky 10 needs x86-64-v3, which a masked guest CPU may not advertise. Version 9 has no such requirement.
Provisioning
Vagrant + a pinned box, not the downloaded ISO. Boxes are pre-installed images; an ISO would need Packer to become one. Terraform's Hyper-V provider and Multipass were both rejected — the first needs WinRM for a local host, the second can't attach the disks a storage layer would want.
CNI
Flannel (k3s default). OVN-Kubernetes was tempting for OpenShift practice, but there's no documented k3s + OVN-K path, nodes stay NotReady until the CNI works, and — decisively — OpenShift never has you install OVN-K by hand. The Cluster Network Operator does it. Hand-rolling the install teaches the one part that doesn't transfer.
Storage
local-path, on a dedicated disk. Rook/Ceph became its own project: three OSDs on one SSD gives no real redundancy, and Ceph's default 4 GB osd_memory_target would OOM these nodes. But the box's 8.9 GB root cannot hold this stack's images, so each node gets a 30 GB disk mounted at /var/lib/rancher — containerd, the kubelet and local-path PVs all live there. Dynamically allocated, so the unused space costs nothing.
Gateway provider
agentgateway, not Istio or kgateway. kgateway is deprecated and scheduled for removal, so learning it would be learning a dead path. Istio is the documented default but carries a footprint these 6 GB nodes would feel. agentgateway is where llm-d is heading — newer and less documented, which is a real cost, but the right thing to be fluent in.
Secrets
Generated, never committed. The k3s join token is produced at build time into a gitignored file rather than written into the Vagrantfile. Same for the kubeconfig, which carries admin certificates. A public repository that rebuilds a whole cluster from one command must not also hand over the keys to it.
Working with the cluster
kubectl from inside the cluster. No local kubectl on the Windows host — vagrant ssh k3s-server and work there. One less kubeconfig to keep in sync, and no risk of pointing the wrong context at a different cluster.
Where the disks live
C: — the NVMe, despite the 4 TB HDD having more room. The gap is roughly 1000× in random IOPS, and three VMs on one spindle means head thrash. Linked clones and dynamic allocation put the real footprint near 40–80 GB against 1566 GB free — the space argument never applied.

Verification gates

Facts to establish from the running VMs before phase 3. Each one can invalidate an assumption above.

  • What AVX flags survive into the guest. Determines whether ollama is usable and settles the vLLM question with evidence rather than reasoning. avx avx2 — no AVX-512. Prediction confirmed: vLLM ruled out, ollama viable.
  • Real interface names. Rocky normally uses predictable names, but Vagrant boxes often disable that — the answer changes the k3s flags. eth0 = NAT 10.0.2.15 · eth1 = host-only. Box disables predictable naming.
  • Node-to-node reachability across the host-only network. 0% loss both directions. ~10 ms avg — high for a virtual switch, the compatibility-mode tax.
  • Swap reads 0B on every node, and the /etc/fstab entry stayed commented. 0B on all three. SELinux Enforcing, firewalld inactive, as intended.
  • Kernel matches userspace. Release reports 9.8 but the running kernel is still el9_5 — a newer one is installed and waiting on a boot. Pending: one vagrant reload before k3s goes on.

Living document — phase states and gate results update as the build proceeds. Written alongside the work, so the reasoning survives into the write-up rather than being reconstructed afterwards.
